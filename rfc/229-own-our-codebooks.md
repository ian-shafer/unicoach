# RFC 229 — Own our codebooks: seed them at migration time

**Slice:** `test/05.3/own-our-codebooks` (brief 0010, D27) **Lane:** A (rfc) — a
data-placement change plus two schema constraints. **Base:** `main@9870374e`

## Summary

The published-codebook tables of `0060` are unicoach's own reference data. Today
they are CREATED by a migration and FILLED by the data-import run
(`CodebookLoader`, the `codebooks` phase of `bin/ingest-colleges`), so on a
freshly migrated database they are EMPTY — and anything else seeded by a
migration cannot key into them. `test/05` proved it as a hard failure: 112 of
113 migrations applied and the seed was refused with
`Key (state)=(AL) is not present in table "us_states"`. That is a fresh
PRODUCTION database too, not only a test one.

Ian named the defect rather than the workaround:
_"`filled by the data-import
run` this is the problem. Unicoach owns the
us_states table. so it should populate it."_ (D27.)

This RFC moves WHEN the codebooks are written, never WHAT they say. One
generated migration places every published codebook row from the same committed
file the ingest reads (`db/data/codebooks.json`), and a second migration adds
the two foreign keys that could not exist before — deleting the interim
`^[A-Z]{2}$` format rule rather than leaving it beside a key that is strictly
stronger (RFC 208's own reasoning).

**Correction recorded, not papered over:** this slice adds NO table. The
dispatch template said it would; measured against the tree, it does not. No
`CREATE TABLE` appears anywhere in the change. What it adds is data and two
constraints, which the gate DDL below shows in full.

**Second correction:** the brief said the codebooks come "from authored files".
One column in the whole corpus is authored by hand —
`us_states.jurisdiction_kind`, which says DC is a federal district and Palau is
not a US territory. Everything else is generated by `bin/fetch-codebooks` from
the committed IPEDS archives. The committed file exists and is reviewed in
diffs; the seed is an artifact of it. The pattern holds; the word "authored"
does not.

No user-visible change. No coach prompt edit, so no prompt version is cut.

## Detailed Design

### 1. The source is already committed, and it is already generated

`db/data/codebooks.json` (394 KB, committed, 10 domains, 2,015 rows) is produced
by `bin/fetch-codebooks` from the IPEDS Stata archives under
`db/seed/codebooks/`, which are committed with a `PROVENANCE.json` and a sha256
per artifact. So the seed is generated from a generated file, and the chain from
publisher to row stays reviewable end to end. Nothing is re-typed.

The eleventh table, `codebook_sources`, is not a domain in that file: it is the
per-domain header (`source`, `source_file`, `source_sha256`,
`source_vintage_year`, `null_sentinels`) that `CodebookLoader` writes as one row
per domain. The seed writes it the same way, so the drift guard has a baseline
from the first migration rather than from the first ingest.

### 2. `bin/codebook-seed` — the generator

A new script on the `bin/test-calendar-seed` / `bin/test-state-programme-seed`
model, and deliberately the same shape rather than a third invention. It is
Python 3, stdlib-only, because the source is JSON and a bash generator would
have to re-implement a JSON parser; it follows the `bin/` conventions exactly
(getopt grammar via the shared `pyfunctions`, all diagnostics on stderr, nothing
on stdout except the `-h` text).

- reads `db/data/codebooks.json`, writes
  `db/schema/seed-published-codebooks-r<N>.sql`;
- the revision N is one past the highest committed revision, and a new file is
  cut only when the body differs from the newest — the `bin/prompt-seed` rule;
- `-n` regenerates into memory and exits 3 (`EXIT_SEED_WOULD_CHANGE`) when the
  committed seed differs, 0 when it matches;
- validates before it writes and reports EVERY fault in one pass: each CHECK
  constraint in `0060` is mirrored (slug grammar, `jurisdiction_kind` set,
  locale `type`/`detail` sets, `assoc[1-6]` source variable, six-digit CIP code,
  sha256 grammar, vintage range), plus the two cross-domain facts the migration
  relies on — every `us_states.ipeds_region` resolves to an `ipeds_regions`
  slug, and no declared `null_sentinel` is also published as a code (D41).

`bin/db-migrate` records applied migrations BY FILENAME, so a refreshed codebook
is a NEW revision file and a new `ORDER` line — editing a landed seed would
change a fresh database and leave every existing one behind. Measured, not
estimated: the generated file is 207,393 bytes, 2,015 vocabulary rows plus 10
source rows, of which `cip_codes` is 1,710.

### 3. `db/schema/seed-published-codebooks-r1.sql` — the generated seed

One migration, ten `INSERT ... ON CONFLICT (<natural key>) DO UPDATE` statements
plus `codebook_sources`, in dependency order (`ipeds_regions` before
`us_states`, which references it). The ten vocabulary tables use the same
`WHERE (...) IS DISTINCT FROM (EXCLUDED...)` change guard as
`CodebooksDao.upsertDetectingChange`, so applying against rows an ingest already
placed is a true no-op — no `updated_at` bump, no phantom CHANGED.
`codebook_sources` is the loader's one exception and always moves `loaded_at`,
exactly as `CodebooksDao.upsertSource` does.

The full shape, and one representative row per domain, is in
[§ The DDL, in full](#the-ddl-in-full).

### 4. `db/schema/key-state-columns-to-us-states.sql` — the keys

Appended after the seed (dependency order in `ORDER`). Two foreign keys and one
dropped CHECK:

- `admission_test_state_programmes.state` — the named debt. `test/05` shipped
  the interim `^[A-Z]{2}$` rule with Ian's approval and the promise that the key
  arrives here. The CHECK is DROPPED in the same migration: a key is strictly
  stronger than a regex, and two rules for one fact is the duplication RFC 208
  itself argues against. `'ZZ'` passes a regex and is nobody's jurisdiction.
- `fafsa_filing_deadlines.state` — the same debt, written down in that table's
  own column comment: _"test/05.3 adds the key here and on
  admission_test_state_programmes together."_ The column is NULLABLE (the
  FEDERAL row), which a foreign key permits. Its comments are rewritten to say
  what is now true.

`ON DELETE RESTRICT` on both: a codebook row that something cites may not be
deleted. That is the same answer `CodebookLoader.ReferencedCodebookRowException`
already gives one layer up, now held by the database.

NOT done, and recorded so nobody re-proposes it: `college_search_index.state` /
`.locale` / `.test_policy` keep the decision `0064` made for them, and the
`college_ipeds` code columns keep the range CHECKs D46 gave them. Those columns
are filled BY the ingest, and the unknown-code question they raise is the
follow-on in the next section, not this slice.

### 5. The import keeps running, and its job is to ACCOMMODATE the publisher

Ian's decision, in his words: _"Typically, Unicoach should just add the new
rows. But those new rows should be reviewed by a human."_ and _"The idea here is
that the Unicoach system should accommodate the external data. If it does not,
it should probably be updated."_

So `CodebookLoader` and the `codebooks` phase stay, but the RFC does not cast
them as a guard standing between us and the publisher. Their job after this
change is to take what the publisher now publishes:

- the migration seeds a BASELINE so a freshly built database is complete and can
  be keyed against (D27, unchanged);
- the import ADDS new rows when a refreshed codebook carries codes the baseline
  did not;
- **the human review is the committed diff.** `db/data/codebooks.json` is
  committed, so a regenerated codebook that adds rows produces a reviewable diff
  before anything ships. That review already exists; this slice builds no second
  review mechanism (D28: do not build the fifth mechanism);
- the refusals that remain are only what the database itself cannot express: an
  archive whose bytes no longer match their recorded fingerprint, and a sentinel
  like "unknown" arriving dressed as a real value. A label a college row still
  points at is now a FOREIGN KEY violation at the database, not a script's
  judgement.

The acceptance test pins the consequence: re-applying the generated seed over
the migrated rows changes no codebook VALUE (§ Tests).

### 6. The unknown-code behaviour is MEASURED AND REPORTED, not changed here

Measured, not theorised. Today an IPEDS code with no codebook row is silently
NULLed where the search index is rebuilt:

- `CollegesDao` rebuilds `college_search_index` with LEFT JOINs on the codebook
  tables by `code` (`CollegesDao.kt:3018-3020`: `ipeds_regions`, `nces_locales`,
  `admission_test_policies`), so a code absent from a codebook yields a NULL
  slug in the index;
- `CodebookLoader.reportUnknownCodes` reports those stored-but-unexplained codes
  per column, with counts, as a log warning after the ingest;
- `CollegeSearchIndexRebuildTest.kt:411`
  (`a college whose region code has no
  codebook row survives with region NULL`)
  and `:424`
  (`every coded column
  tolerates an unknown code and none of them drops the college`)
  pin the surviving-but-NULL behaviour, and
  `CodebookReferenceFixture.OMITTED_REGION` deliberately omits
  `other-us-jurisdictions` so the test has a real absent code to probe with.

Under Ian's rule that is us deciding the publisher is wrong: a published code we
do not yet hold becomes an unexplainable NULL instead of a row. **Not changed in
this run**, per instruction. Accommodating it would mean one of: the ingest
INSERTING a placeholder codebook row for a stored code it does not recognise
(flagged as data-derived rather than codebook-authored, which needs a provenance
marker the tables do not have), or the index rebuild carrying the raw code plus
a "no label yet" marker instead of NULL (which changes the filter contract).
Flagged to Ian as its own slice; the cost is a new provenance shape, not a
migration.

### 7. Test fixtures are deliberately NOT changed

`CollegeScorecardTestBase.resetDatabase` truncates the codebook tables and
re-seeds a PARTIAL set from `CodebookReferenceFixture`, which omits region 9 and
its eight territory/COFA jurisdictions on purpose. That stays. A suite that
truncates a table the migration filled is making a deliberate statement about
its own preconditions, and the guarantee this slice adds is about a database the
migrations built, not about a table mid-suite.

One consequence is named because it is new and silent: the base's
`TRUNCATE ... us_states ... CASCADE` now also truncates
`admission_test_state_programmes` and `fafsa_filing_deadlines`. No suite today
reads the migration-seeded rows of either table from a shared database — the
state programme guard reads the committed FILE, and the DAO suites insert and
re-seed their own rows in `@BeforeEach`. The acceptance test therefore does NOT
live in Gradle at all: a test asserting "the migrated database holds 59 states"
inside a suite another suite may have truncated is a test measuring run order.
It lives in `bin/db-scripts-tests`, which owns a private database.

## Implementation Plan

1. `bin/codebook-seed`, with its validators and `-n`; generate the seed.
2. `db/schema/key-state-columns-to-us-states.sql`; append both `ORDER` lines in
   dependency order (seed, then keys).
3. `nix develop -c bin/db-reset` in the worktree: the whole corpus applies from
   scratch, including `test/05`'s seed and both keys. This is the case that
   failed; it must pass before anything else is written.
4. `bin/codebook-seed-scripts-tests` + the `bin/gate-scope` and
   `bin/shell-tests` wiring.
5. The `bin/db-scripts-tests` acceptance section.
6. Comment edits on the two create migrations.
7. `nix develop -c bin/test`, then the hook.

## Tests

**The acceptance criterion is the case that failed, and it is proved on a
database built by migration alone.** `bin/db-scripts-tests` already owns a
private throwaway database, so the test there drops it, recreates it, and runs
the real `db/schema` corpus — no ingest, no fixture. It asserts:

- `us_states` holds 59 rows, `ipeds_regions` 10, `nces_locales` 12, `cip_codes`
  1,710, `codebook_sources` 10;
- every `admission_test_state_programmes.state` resolves to a `us_states` row
  (zero orphans);
- an `UPDATE` of a programme row to `state = 'ZZ'` is refused by the foreign key
  (the case the interim regex accepted);
- a FAFSA deadline insert with `state = 'ZZ'` is refused, and one with
  `state = NULL` is accepted (the FEDERAL row);
- **no codebook row changes value**: a checksum over every data column of every
  codebook table (timestamps excluded) is identical before and after re-applying
  the generated seed. The seed's upsert is the identical
  `WHERE ... IS DISTINCT FROM ...` shape `CodebooksDao` runs, so this is the
  migrated-only vs migrated-then-re-ingested pin.

`bin/codebook-seed-scripts-tests` (new, no database) asserts the generator
itself: the usage band, stdout silence on a normal run,
write-nothing-on-refusal, the four validator refusals (bad slug, bad
`jurisdiction_kind`, unresolved `us_states.ipeds_region`, sentinel-as-code) plus
a three-fault file reported in one pass, and `-n` exiting 0 against the
committed tree and 3 against a valid but different copy.

No change to the Kotlin suites is required: `CollegeScorecardTestBase` already
truncates the codebook tables before every test and reseeds its partial fixture,
which is exactly the precondition `CodebookLoaderTest` needs for its first-load
insert counts.

Counts are read from the JUnit XML `tests=` attribute, never from
`grep -c "@Test"`.

## What this does not do

- No new table, no column, no user-visible change, no coach prompt edit, so no
  prompt version is cut.
- No date is rendered for a human anywhere in this slice, so D21 (one date seam)
  adds nothing to enforce here.
- The unknown-code NULLing is measured and reported, not changed (follow-on).
