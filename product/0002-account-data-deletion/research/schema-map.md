# Schema map for account erasure

Research report for brief 0002 (account data deletion). Written 2026-10-30
against `main@00bdeb7e`. Replaces the "What the schema does today (investigated
2026-08-25)" section of `brief.md`, which predates the family, test-score,
intended-subject, sharing-permission and subscription-rekey migrations.

Every claim cites `db/schema/<file>:<line>`. Nothing here describes what
application code does; a separate report covers the Kotlin side.

## Method

1. Read `db/schema/ORDER` end to end (167 files). Every migration that creates
   or alters a table was read in full; the `seed-*` prompt and reference-data
   seeds were skipped, as were the reference-data migrations that touch only
   college / codebook / money-publisher tables (0015, 0045, 0051-0067, 0075,
   0077, 0083-0094, `record-source-url-status`, `create-admission-test-*`,
   `add-college-*`, `create-external-documents`, `adopt-external-documents-*`,
   `create-fafsa-*`, `key-state-columns-*`, `create-program-money-stats`,
   `create-college-automatic-awards`, `add-eight-year-*`,
   `create-national-merit-cycles`, `create-college-national-merit-awards`,
   `require-a-check-*`) — those were grepped, not read, for any `REFERENCES`
   onto `users`, `students`, `supporters` or `convos`, any `user_id` /
   `student_id` / `supporter_id` column, and any `email` / `name` column. None
   was found in them.
2. Read `0000.shared-functions.sql` plus every later file that defines a guard
   function (0006, 0007, 0023, `supporters-and-student-links.sql`,
   `supporter-link-requests.sql`,
   `user-auth-identities-delete-on-closed-account.sql`, `convos-party.sql`,
   `create-sharing-permissions.sql`, `intended-subjects.sql`).
3. For each table, the shape recorded is the LIVE shape after all migrations:
   dropped columns (0017, 0039, 0040, `create-partial-date-storage.sql`,
   `subscriptions-key-on-account.sql`), dropped tables (0039, 0087), redefined
   trigger functions (0012, 0013, 0017, 0023, 0070, 0071, 0078,
   `add-students-date-of-birth.sql`, `subscriptions-key-on-account.sql`) and
   replaced triggers (`user-auth-identities-delete-on-closed-account.sql`) are
   all folded in.
4. Cross-checked with three greps over the whole directory: every
   `REFERENCES (users|students|supporters|convos|…)`, every `BEFORE DELETE ON`,
   and every `CREATE TABLE` / `CREATE VIEW`. The closing section lists every
   table those greps found so the coordinator can see nothing was skipped.

Terminology used below:

- **NO ACTION** means the FK states no `ON DELETE` clause (Postgres default,
  checked at statement end — blocks the parent delete while a child row exists).
- **Delete guard** means a `BEFORE DELETE` row trigger that raises. Postgres
  fires row-level `BEFORE DELETE` triggers on rows removed by an
  `ON DELETE
  CASCADE`, so a CASCADE into a guarded child is refused by the
  child's guard; only `TRUNCATE` (0039:12-15, 0040:19-21) and
  `ALTER TABLE … DISABLE TRIGGER` (0035:48, `add-students-date-of-birth.sql:33`)
  have precedent for bypassing row guards in this schema.
- **frozen** means a per-table `BEFORE UPDATE` trigger refuses a change to that
  column (so it cannot be re-pointed at a tombstone account by UPDATE).

### C.3 The precedent for a conditional delete guard

`user-auth-identities-delete-on-closed-account.sql` (RFC 252, section 1b) is the
only place in the schema where a delete guard is relaxed by STATE rather than
removed. It admits a DELETE exactly when the owning `users` row is soft-deleted,
and names its own constraint so a DAO can route on it. The trigger body,
verbatim (:24-39):

```sql
CREATE OR REPLACE FUNCTION prevent_live_user_auth_identities_delete()
RETURNS TRIGGER AS $$
BEGIN
    IF EXISTS (
        SELECT 1 FROM users u
         WHERE u.id = OLD.user_id AND u.deleted_at IS NOT NULL
    ) THEN
        RETURN OLD;
    END IF;
    RAISE EXCEPTION
        'An auth identity may be deleted only for a closed account: identity [%], user [%].',
        OLD.id, OLD.user_id
        USING ERRCODE = 'P0001',
              CONSTRAINT = 'user_auth_identities_owner_closed';
END;
$$ LANGUAGE plpgsql;
```

It replaces the original unconditional guard by name (:41-45), leaving the
update guard untouched (:18). The stated reason (:4-13) is that the TOTAL unique
`(provider, subject)` index kept a closed account's Apple/Google subject
forever, so the person could never sign up again. The same shape — "a DELETE is
admitted only when the owning account is closed" — is the schema's own template
for every other guard an erasure path must pass.

Two other bypass precedents, both DDL-level rather than row-level:
`ALTER TABLE … DISABLE TRIGGER <name>` / `ENABLE TRIGGER` around a one-time
backfill UPDATE on a log table (0035:48-53, 0035:74-79) and
`DISABLE TRIGGER
USER` on `students` (`create-partial-date-storage.sql:63-75`,
`add-students-date-of-birth.sql:33-37`); and `TRUNCATE … CASCADE`, which does
not fire row-level delete guards (0039:11-17,25; 0040:19-21,27,45,68).

## E. Surprises for an erasure design

### E.1 FKs with no ON DELETE clause that block a physical delete

Of `users`: `students.user_id` (0005:13), `verification_tokens.user_id`
(0014:13), `supporters.user_id` (`supporters-and-student-links.sql:44`),
`subscriptions.user_id` (`subscriptions-key-on-account.sql:54`). The comments at
`supporters-and-student-links.sql:41-43` and
`subscriptions-key-on-account.sql:18-23` state this is deliberate: "users are
never physically deleted … a cascade would never fire".

Of `supporters`: `supporter_student_links.supporter_id` (:67),
`convos.supporter_id` (`convos-party.sql:26`),
`supporter_llm_costs.supporter_id` (`supporter-llm-cost.sql:24`).

Of `supporter_student_links`: `supporter_link_requests.link_id`
(`supporter-link-requests.sql:43`).

Of `llm_requests` (the table that holds the words): all six owner edges are NO
ACTION — `convo_requests.llm_request_id` (0039:32),
`extraction_runs.llm_request_id` (0040:30), `synthesis_runs.llm_request_id`
(0040:48), `fit_lens_runs.query_llm_request_id` / `reason_llm_request_id`
(0040:71-72), `supporter_llm_costs.llm_request_id`
(`supporter-llm-cost.sql:23`). So the call log cannot be pruned from the top
while any owner row exists, and the design must delete owners first — see E.3.

Of `convos`: `commitments.disclosed_in_convo_id` and
`fit_suggestions.surfaced_in_convo_id` are RESTRICT (0025:47, 0031:45), so a
fulfilled commitment or a surfaced suggestion pins the conversation it was
surfaced in even though both tables CASCADE from `students`.

Of `claims`: `claims.superseded_by_id` is a RESTRICT self-reference (0019:75): a
chain of superseded claims must be deleted newest-first.

### E.2 Account-id columns with no FK (neither CASCADE nor a schema walk finds them)

`students_versions.user_id` (0005:46); `supporters_versions.user_id`
(`supporters-and-student-links.sql:121`); `subscriptions_versions.user_id`
(`subscriptions-key-on-account.sql:58`);
`supporter_student_links_versions.supporter_id` and `.student_id` (:136-137);
`college_list_entries_versions.student_id` (0024:65);
`money_profiles_versions.student_id` (0046:73);
`admission_test_scores_versions.student_id`
(`create-admission-test-scores.sql:163`);
`sharing_permissions_versions.student_id` (`create-sharing-permissions.sql:80`);
`intended_subjects_versions.student_id` (`intended-subjects.sql:125`);
`intended_subject_status_versions.student_id` (:141). Each is reachable only
through its `id → live row` RESTRICT edge, i.e. by walking from the live row,
never from the account.

Opaque JSONB that may carry ids but cannot be walked: `jobs.payload` (0003:6),
`periodic_jobs.payload` (0029:21), `sessions.metadata` (0002:16),
`llm_requests.content` / `tools` / `params` (0038:36-40).

### E.3 Person-authored text in tables with NO account key

`llm_requests.system` and `llm_requests.content` (0038:35-36) hold every message
the student or parent typed and every reply, verbatim; `llm_responses.content`
(0038:81) holds the model's output about them; `llm_responses_raw.payload`
(0038:126) is the raw provider body. None of the three has a `student_id` /
`user_id` / `supporter_id`. They are reached only through the owner rows of E.1
— and every one of those owner rows CASCADEs from `students` (`convos` →
`convo_requests`; `extraction_runs`; `synthesis_runs`; `fit_lens_runs`) or sits
under `supporters`. A physical delete of the owners would therefore leave the
text behind as unkeyed orphans, exactly the "crash-window orphan" shape
0040:95-97 describes as invisible to the cost views. An erasure design has to
collect `llm_request_id`s from the owners BEFORE removing them.

Also keyless: `email_sends.recipient_email` / `body` (0008:18,21) — every
verification, invite and link-request email, with the recipient address, in an
append-only table with no account key.

### E.4 Denormalised copies of identifying data

- `users_versions`: full history of `email`, `name`, `display_name`,
  `password_hash` (0001:55-58); scrubbing `users` writes a NEW version row and
  leaves every older one intact (0001:78-90).
- `user_auth_identities.email` — the provider's email at link time, "never
  re-synced" (0018:8-11,24).
- `email_sends.recipient_email`, `sender_email`, `body` (0008:18-21).
- `convos.name` — derived from the first user turn (0006:59-61).
- `observations.quote` (0019:33), `claims.statement` (0019:72),
  `commitments.statement` / `drop_reason` (0025:42,49),
  `fit_suggestions.rationale` (0031:42), `college_list_entries.reasons`
  (0024:39) and its versions (0024:68): free text derived from what the person
  said, each keyed by `student_id` but each also independently readable.
- `extraction_runs` / `synthesis_runs` / `fit_lens_runs.failure_reason`
  (0035:46,72; 0034:21): diagnostic free text that may quote model output.
- `sessions.user_agent`, `initial_ip` (0002:14-15).
- `students.date_of_birth` plus its versions; `money_profiles.residency_state`
  and `income_band` plus their versions.

### E.5 Rows that hold keys from TWO accounts

- `supporter_student_links` (`supporter_id` + `student_id`,
  `supporters-and-student-links.sql:67-70`) and
  `supporter_student_links_versions` (:136-137). Deleting either party's account
  must decide what the other party's history shows.
- `supporter_link_requests` (`supporter_id`, `student_id`, and
  `cost_report_share_id` which belongs to the student;
  `supporter-link-requests.sql:34-36`); DELETE is refused outright, so a closed
  account's request rows persist with both ids. The comment at :25-28 says "app
  code closes accounts by soft delete and cancels the pending requests itself".
- `supporter_invites` (`inviter_user_id` + the inviter's own `student_id` or
  `supporter_id`; `supporter-invites.sql:16-24`). The invitee is not recorded,
  so this is one account's keys in two forms, not two accounts — but after
  acceptance the resulting link row is the two-account record.
- `convos` where `party = 'supporter'`: `student_id` (about whom) and
  `supporter_id` (with whom) on one row (`convos-party.sql:18-30`). Everything
  beneath such a convo — `convo_requests`, their `llm_requests.content` (the
  PARENT's words), `llm_responses` — is keyed to the STUDENT through
  `convos.student_id` and CASCADEs from `students`, while its cost is keyed to
  the supporter through `supporter_llm_costs`. The schema also permits
  `observations` / `extraction_runs` rows (keyed by `student_id` AND `convo_id`,
  0019:28-29,151-152) to point at a supporter convo; whether extraction ever
  runs on one is an application question.
- `supporter_llm_costs` (`supporter_id`) ↔ the convo's `student_id`, joined
  through `llm_request_id → convo_requests → convos`.
- `account_llm_cost` collapses both sides onto `users.id`
  (`account-llm-cost.sql:32-55`): the spend of a user who is both student and
  supporter is one total.

### E.6 Uniqueness and liveness rules an erasure path trips over

- `students_user_id_unique_idx` (0005:36) and `supporters_user_id_unique_idx`
  (`supporters-and-student-links.sql:50`) are TOTAL, not partial on
  `deleted_at`: a `users.id` can never acquire a second `students` or
  `supporters` row. The comments (0005:33-35, :47-49) justify this by "account
  deletion cascades to the user, so there is no legitimate re-creation path" — a
  claim about a cascade that is in fact blocked (E.1, D.6).
- `users_email_unique_active_idx` IS partial (0001:41), so a soft-deleted
  account's email can be re-registered — but
  `user_auth_identities_provider_subject_idx` is TOTAL (0018:37-38), which is
  why RFC 252 had to admit a delete.
- `subscriptions_original_transaction_id_unique` is TOTAL (0042:50): Apple's id
  for a closed account's subscription can never be re-bound to a new row.
- `prevent_supporter_student_link_closed_endpoint()` fires on INSERT only
  (`supporters-and-student-links.sql:206-211, 382-384`), so an unlink
  (soft-delete UPDATE) of a link to a closed account is allowed; a RE-link to a
  soft-deleted account is refused by name.
- `cost_report_shares`: the raw share token is `HMAC(secret, id)` (0073:11-13).
  A soft-deleted student's unrevoked share row keeps the report link derivable;
  the row has no delete guard (0073:15-23) but `share_events.share_id` and
  `supporter_link_requests.cost_report_share_id` CASCADE onto it (0081:34,
  `supporter-link-requests.sql:36`), and the latter table refuses DELETE — so
  deleting a share row cascades into a guarded table and is refused.
- `intended_subjects` ↔ `intended_subject_status` agreement is judged at COMMIT
  (`intended-subjects.sql:356-369`): a reset that soft-deletes the subjects but
  not the status row (or vice versa) fails the transaction.
- `money_profiles` statuses are typed by the `answer_status` DOMAIN
  (`create-answer-status-domains.sql:86-90`) with a value-iff-answered CHECK
  (:92-100): anonymising a value column to NULL requires flipping its status off
  `answered` in the same statement.
- Every versioned table requires `version = OLD.version + 1` on UPDATE
  (0000:24-28) and writes a new history row, so a scrub is itself a recorded
  event — and the pre-scrub history rows survive (B).

### E.7 Soft-delete coverage is uneven

`deleted_at` exists on `users`, `students`, `convos`, `college_list_entries`,
`money_profiles`, `sharing_permissions`, `intended_subjects`,
`intended_subject_status`, `admission_test_scores`, `supporters`,
`supporter_student_links` (and their versions tables). It does NOT exist on
`claims`, `commitments`, `fit_suggestions` (status lifecycles instead),
`sessions` (`is_revoked`), `subscriptions` (`status`), any log table,
`verification_tokens` / `cost_report_shares` / `supporter_invites` /
`admission_test_score_declines` (`consumed_at` / `revoked_at` / `withdrawn_at`),
or `supporter_link_requests` (`resolution`). A "soft delete the account" step
therefore has no single column to set below `users` / `students` / `supporters`,
and the cost views deliberately ignore `deleted_at` everywhere (0040:99-102,
`account-llm-cost.sql:22-27`).
